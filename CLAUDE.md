## PARA MÁS ADELANTE: repositorios de proyectos individuales (no hacer todavía)

Cuando se aborde cada proyecto por separado, seguir estas pautas:

- **Un repo por proyecto** (o uno por grupo de proyectos pequeños relacionados).
- **README de cada proyecto:** qué problema resuelve, por qué se hizo, stack usado, cómo
  instalarlo/ejecutarlo, capturas o GIF de demo si es posible, resultados si son medibles.
- **Decidir visibilidad según el caso:**
  - Proyectos personales/académicos sin restricciones → repo público completo, con licencia (MIT
    por defecto salvo que se prefiera restringir la reutilización, en cuyo caso simplemente no
    poner licencia — por defecto GitHub aplica "todos los derechos reservados": visible pero no
    reutilizable legalmente).
  - Proyectos con propiedad intelectual de terceros (ej. cualquier cosa del Ford — Spx for SPOT,
    Sentinel EU) → **nunca publicar el código**. Usar formato "case study": documentar problema,
    arquitectura, decisiones técnicas y resultados en el README, sin código fuente ni fragmentos
    sensibles. Si hay dudas sobre qué se puede contar, revisar antes si hubo NDA o acuerdo de
    confidencialidad.
  - Proyectos que se quieren enseñar completos pero solo a una empresa concreta durante un
    proceso → repo privado + invitar como colaborador temporal a esa persona/reclutador.
- **Buenas prácticas generales:** commits descriptivos, `.gitignore` adecuado (no subir claves,
  datasets pesados o configuración interna), estructura de carpetas limpia, topics/tags en GitHub
  para que se puedan filtrar por tecnología.
- Al terminar cada repo, volver a este `README.md` de perfil y sustituir el TODO correspondiente
  por el enlace real.
